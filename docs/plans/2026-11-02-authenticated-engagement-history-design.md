# Authenticated Engagement History Design

**Date:** 2026-11-02  
**Work unit:** WU-ENG-1  
**Status:** Approved  
**Delivery stage:** Stage 2 — Web listening and engagement

## 1. Decision summary

BeatzClik will persist listening history only for authenticated accounts. Signed-in listeners receive
cross-device sessions, Recently Played, podcast Continue Listening, resume positions, history
clearing, and a future-history opt-out. Anonymous playback remains supported by the existing playback
APIs, but anonymous history and resume state remain device-local. This work does not merge anonymous
device history into an account after sign-in.

Engagement is a new hexagonal module. It owns behavioral history and privacy-safe engagement
aggregates. It does not write playback's `play_event`, grant ownership, post ledger entries, or decide
royalties. Catalog and podcast data are resolved through narrow reader ports; the engagement module
does not read another module's tables or create cross-module foreign keys.

Checkpoint ingestion uses a hybrid projection model:

1. A short transaction inserts an immutable checkpoint and updates personal progress.
2. The unique `(session_id, sequence)` key makes retries idempotent.
3. Only a checkpoint whose sequence advances the session is effective. Late checkpoints remain
   diagnostic records but cannot change progress or aggregates.
4. A scheduled projector converts effective checkpoints into anonymous daily aggregates. Projection
   is eventually consistent and idempotent.

The implementation must record the new module boundary as an ADR in
`backend/docs/00-system-architecture.md` and add `backend/docs/architecture/engagement.md`.

## 2. Alternatives considered

### Extend `playback`

This is initially smaller, but it mixes financial counted plays with behavioral history. Privacy
deletion and podcast resume would then live beside royalty-sensitive logic, increasing the chance that
a future change accidentally affects revenue. Rejected.

### Send all activity directly to `analytics`

This centralizes events, but analytics is optimized for aggregates rather than mutable personal state.
Recently Played, opt-out, erasure, and cross-device resume would become awkward projections owned by
the wrong module. Rejected.

### Dedicated `engagement` module with hybrid projection

This keeps personal state, privacy lifecycle, and aggregate production together while preserving a
hard boundary from money. Personal resume updates are immediate; aggregate contention and reporting
latency are moved off the request path. Selected.

## 3. Scope and non-goals

### In scope

- authenticated listening sessions;
- track and podcast-episode checkpoints;
- `start`, `qualified-play`, `progress`, `completion`, `skip`, and `repeat` events;
- session-local monotonic sequencing and idempotent retries;
- de-duplicated Recently Played;
- podcast Continue Listening and meaningful resume positions;
- history recording preference and full personal-history clearing;
- anonymous daily content aggregates;
- retention and privacy boundaries documented in the API and architecture.

### Not in scope

- durable anonymous history or anonymous identity cookies;
- importing browser-local history at sign-in;
- recommendations or personalized discovery ranking;
- notification fanout;
- creator access to raw listener history;
- financial play qualification, ownership, royalties, or ledger activity;
- mobile synchronization beyond consuming the same authenticated API later.

## 4. Module structure

The module follows the existing adapter → application → domain dependency direction.

### Inbound ports

- `StartListeningSession`
- `IngestListeningCheckpoint`
- `GetRecentlyPlayed`
- `GetContinueListening`
- `GetListeningPreference`
- `UpdateListeningPreference`
- `ClearListeningHistory`
- `ProjectEngagementAggregates`

### Outbound ports

- `EngagementRepository`
- `EngagementContentReader`
- platform `Clock`
- platform `IdGenerator`

`EngagementContentReader` returns only the snapshot needed to validate and render activity: content
kind, ID, availability, title, creator/show label, artwork, and authoritative duration. It supports
batch resolution for history pages so the REST path does not create N+1 lookups. Its adapter may
delegate to catalog or podcasts through their public application ports. There is no repository or JPA
entity sharing.

The REST adapter obtains the account ID from the authenticated principal. Account IDs never come from
request bodies or path parameters. Repository methods always include the account ID when reading or
mutating a session.

## 5. Persistence design

IDs follow the codebase convention: UUIDv7 values generated by `IdGenerator` and stored as `TEXT`.
All times are `TIMESTAMPTZ`. Cross-module references such as account, track, and episode IDs are opaque
`TEXT` values with no foreign keys.

### `listening_preference`

One row per account:

- `account_id TEXT PRIMARY KEY`
- `history_enabled BOOLEAN NOT NULL DEFAULT TRUE`
- `history_cleared_at TIMESTAMPTZ NULL`
- `updated_at TIMESTAMPTZ NOT NULL`

Missing rows mean history is enabled. Updates use atomic `INSERT ... ON CONFLICT DO UPDATE`.

### `listening_session`

- `id TEXT PRIMARY KEY`
- `account_id TEXT NOT NULL`
- `started_at TIMESTAMPTZ NOT NULL`
- `last_checkpoint_at TIMESTAMPTZ NULL`
- `max_sequence BIGINT NOT NULL DEFAULT 0 CHECK (max_sequence >= 0)`
- `closed_at TIMESTAMPTZ NULL`

Index `(account_id, started_at DESC, id DESC)` supports account cleanup and operational inspection.

### `listening_checkpoint`

- `id TEXT PRIMARY KEY`
- `session_id TEXT NOT NULL REFERENCES listening_session(id) ON DELETE CASCADE`
- `account_id TEXT NOT NULL`
- `sequence BIGINT NOT NULL CHECK (sequence > 0)`
- `content_kind TEXT NOT NULL CHECK (content_kind IN ('track','podcast-episode'))`
- `content_id TEXT NOT NULL`
- `event_type TEXT NOT NULL CHECK (event_type IN
  ('start','qualified-play','progress','completion','skip','repeat'))`
- `position_seconds INTEGER NOT NULL CHECK (position_seconds >= 0)`
- `duration_seconds INTEGER NOT NULL CHECK (duration_seconds > 0)`
- `listened_delta_seconds INTEGER NOT NULL DEFAULT 0 CHECK (listened_delta_seconds >= 0)`
- `effective BOOLEAN NOT NULL`
- `received_at TIMESTAMPTZ NOT NULL`
- `aggregated_at TIMESTAMPTZ NULL`

`UNIQUE (session_id, sequence)` is the idempotency boundary. Index
`(account_id, received_at DESC, id DESC)` supports erasure and diagnostics. A partial projector index on
`(received_at, id) WHERE effective AND aggregated_at IS NULL` keeps pending scans small. The projector
also has an index on `session_id` through the unique constraint's leftmost column.

### `listening_progress`

One current row per account and content item:

- `account_id TEXT NOT NULL`
- `content_kind TEXT NOT NULL`
- `content_id TEXT NOT NULL`
- `position_seconds INTEGER NOT NULL`
- `duration_seconds INTEGER NOT NULL`
- `last_event_type TEXT NOT NULL`
- `completed BOOLEAN NOT NULL`
- `last_session_id TEXT NOT NULL`
- `last_sequence BIGINT NOT NULL`
- `last_checkpoint_id TEXT NOT NULL`
- `last_activity_at TIMESTAMPTZ NOT NULL`
- primary key `(account_id, content_kind, content_id)`

Index `(account_id, last_activity_at DESC, content_kind, content_id)` supports keyset pagination.
A partial index with the same order where `content_kind = 'podcast-episode' AND NOT completed` supports
Continue Listening.

### `engagement_daily_rollup`

- `day DATE NOT NULL`
- `content_kind TEXT NOT NULL`
- `content_id TEXT NOT NULL`
- counters for starts, qualified plays, completions, skips, repeats, and listened seconds;
- primary key `(day, content_kind, content_id)`.

This table contains no account or session identifier. Atomic upserts increment counters. It is not a
royalty source.

## 6. Checkpoint transaction and concurrency

The application validates authentication, the positive sequence, recognized event type, non-negative
positions, and content availability before opening the write transaction. The authoritative content
duration comes from `EngagementContentReader`; a client duration is accepted only when it matches the
authoritative duration within a small encoding tolerance. Positions and listened deltas are capped at
the authoritative duration.

Starting the first durable session atomically creates the account's default preference row when it is
missing. Preference changes, checkpoint ingestion, and erasure then lock that row first, giving all
privacy-sensitive writes a consistent serialization point.

Inside one short checkpoint transaction:

1. Lock the account preference row. If history is disabled, return success without persisting.
2. Lock the session row by `(id, account_id)` using `FOR UPDATE`.
3. If the sequence already exists, compare its immutable payload. An exact retry returns success. A
   different payload for the same sequence returns `409 CHECKPOINT_SEQUENCE_CONFLICT`.
4. Insert the checkpoint. It is effective only when `sequence > max_sequence`.
5. For an effective checkpoint, advance `max_sequence`, set `last_checkpoint_at`, and atomically
   upsert `listening_progress`.
6. Commit. No external calls or aggregate writes occur while holding the session lock.

Because sequences are session-local, concurrent sessions cannot compare their sequence numbers.
Progress therefore uses latest server-accepted activity as the cross-session winner. This intentionally
implements "latest activity wins," including deliberate seeks backward on another device.

The aggregate projector claims a bounded batch of effective, unprojected checkpoints with
`FOR UPDATE SKIP LOCKED`. For each row, it increments the UTC daily rollup and sets `aggregated_at` in
the same transaction. A failed batch rolls back without marking any of its rows complete; concurrently
claimed batches remain processable. Multiple projector instances partition work without double
counting.

## 7. API contract

All routes require a fan JWT.

### Start a session

`POST /v1/me/listening-sessions`

- History enabled: `201 { "recording": true, "sessionId": "...", "startedAt": "..." }`.
- History disabled: `200 { "recording": false }`; no session row is created.

### Record a checkpoint

`PUT /v1/me/listening-sessions/{sessionId}/checkpoints/{sequence}`

Request:

```json
{
  "contentKind": "podcast-episode",
  "contentId": "episode-id",
  "eventType": "progress",
  "positionSeconds": 780,
  "durationSeconds": 2400,
  "listenedDeltaSeconds": 15
}
```

An accepted checkpoint, exact retry, or harmless stale sequence returns `204`. A stale unique sequence
is stored with `effective=false` for diagnostics but never changes progress or aggregates. If history
was disabled after the session began, the endpoint returns `204` without persisting the checkpoint.

### Personal reads

- `GET /v1/me/listening/recent?cursor=&limit=` returns keyset-paginated progress rows ordered by
  `(lastActivityAt DESC, contentKind, contentId)` with content snapshots.
- `GET /v1/me/listening/continue?cursor=&limit=` returns only incomplete podcast episodes with a
  meaningful position.

Recently Played de-duplicates by `(contentKind, contentId)` because progress has one row per item.
Continue Listening excludes positions below 10 seconds and episodes considered completed. Completion
means an explicit completion checkpoint or a position at least 95% of authoritative duration.

### Privacy

- `GET /v1/me/listening/settings` returns `{ "historyEnabled": true|false }`.
- `PUT /v1/me/listening/settings` accepts the same field and returns the saved setting.
- `DELETE /v1/me/listening/history` returns `204`.

Changing `historyEnabled` to false deletes sessions, checkpoints, and progress in the same operation;
it is both an opt-out and an erasure of personal history. Clearing history performs the same deletion
but does not change the preference. Aggregate rows committed before erasure remain because they have
no account identifier. Deleted checkpoints cannot participate in future aggregate rebuilds.

## 8. Errors and security

- `401` for missing or invalid authentication.
- `404 SESSION_NOT_FOUND` for an absent session or a session owned by another account.
- `404 CONTENT_NOT_FOUND` for absent or unavailable content.
- `409 CHECKPOINT_SEQUENCE_CONFLICT` when the same session sequence is reused with a different
  immutable payload.
- `422 VALIDATION_ERROR` for an invalid event type, non-positive sequence, impossible position,
  duration mismatch, or listened delta outside allowed bounds.

The API never returns another account's identifiers or activity. Creator and admin APIs cannot query
`listening_session`, `listening_checkpoint`, or `listening_progress`; future analytics adapters may
read only `engagement_daily_rollup`. Logs and metrics must not include account/content history payloads.
Operational metrics expose only counts, latency, projector lag, failures, and queue depth.

## 9. Financial and ownership isolation

The existing optional-auth `POST /v1/tracks/{id}/play` remains the only counted-play entry point. The
web player may call both APIs for different purposes, but neither invokes the other. The engagement
module has no dependency on `RecordPlay`, ledger ports, ownership mutation ports, or payment services.

Architecture and integration tests must prove that checkpoint ingestion does not insert `play_event`,
change ownership grants, or create ledger postings. `qualified-play` in engagement is a behavioral
signal and must never be described as a royalty-qualified play.

## 10. History clearing and projector races

Erasure deletes preference-owned personal rows in a short transaction. The projector processes and
marks each claimed checkpoint in a transaction that also increments the anonymous rollup.

- If projection commits first, its anonymous total remains and erasure then removes the source row.
- If erasure commits first, the projector cannot claim the deleted row.
- If the transactions overlap, row locking serializes their result into one of those two outcomes.

This matches the approved policy: future rebuilds exclude cleared history, while already-anonymized
totals are not subtracted. The system does not retain a per-account aggregate contribution ledger,
because doing so would undermine the privacy boundary it is intended to create.

## 11. Test strategy

### Unit tests

- sequence advancement, exact retries, conflicting retries, and stale checkpoints;
- progress completion and 95% threshold;
- 10-second meaningful-resume threshold;
- history-enabled default and preference transitions;
- aggregate counter mapping for every event type;
- duration and position validation.

### PostgreSQL integration tests

- unique `(session_id, sequence)` enforcement;
- two concurrent requests for the same sequence produce one checkpoint;
- out-of-order checkpoints cannot regress progress or inflate rollups;
- concurrent sessions follow latest-accepted activity;
- two projector workers do not double count;
- projector failure leaves a checkpoint retryable;
- clear-versus-project races produce an allowed serialized outcome;
- opt-out deletes personal rows and blocks later persistence;
- keyset pagination has no duplicates or gaps at stable ordering boundaries;
- account A cannot read or mutate account B's session;
- checkpoint ingestion leaves `play_event`, ownership, and ledger tables unchanged.

### Contract and architecture tests

- OpenAPI shapes and documented status/error codes;
- authentication required on every engagement route;
- domain has no framework dependencies;
- no cross-module repositories, entities, table access, or foreign keys;
- creator/admin surfaces expose aggregates only.
